# 매일 해설 기사 쓰는 법

클라우드 예약 에이전트가 매일 낮 12:17(KST)에 이 문서를 읽고 그대로 따른다.

시각을 낮으로 잡은 이유: 신문 빌드는 08:00 예약이지만 깃허브 크론이 몇 시간씩
밀린다(2026-09-09 실측 10:00). 09:37 에 돌렸더니 그날 수집분이 아직 없었다.

## 이 신문이 무엇인가

괌·사이판·하와이·베트남·코타키나발루·라오스·제주·일본·태국·대만 열 곳의
여행 뉴스를 매일 아침 8시(KST) 자동 발행한다. 기사는 세 등급이다.

| 등급 | 무엇 | 누가 |
|---|---|---|
| A | 우리가 공개 API 로 모은 사실(환율·날씨) | 자동 |
| B | 남의 기사 인용 — 제목 + 200자 이내 + 출처 링크 | 자동 |
| **C** | **해설. 우리가 직접 쓰는 글** | **너** |

B등급은 다른 매체도 다 갖고 있다. **이 신문이 검색에서 살아남는 유일한 이유가
C등급이다.** 네가 쓸 것이 이것이다.

## 1단계 — 소재를 찾는다

`data/items/*.jsonl` 에 날짜별 수집분이 있다. 한 줄이 기사 하나다.

```
id  grade  region  section  title  summary  source_name  source_url  related
```

최근 7~10일치를 읽고 **기사 하나로는 안 보이는 것**을 찾는다.

- **여러 날에 걸친 흐름** — 같은 사안이 며칠에 걸쳐 번져나간 경우. 날짜순으로
  이으면 개별 기사에는 없는 결론이 나온다.
- **여러 매체가 몰린 사건** — `related` 가 길다. 그날의 최대 뉴스다.
- **서로 어긋나는 자료** — 두 조사가 다른 답을 냈다. 왜 다른지가 기사다.
- **같은 조사가 여러 번 실린 경우** — 기사 수와 조사 수는 다르다.
- **여행자에게 실제로 뭐가 바뀌나** — 업계 발표를 보도자료대로 옮기지 말고,
  지금 예약하는 사람에게 무엇이 달라지는지(또는 달라지지 않는지)를 따진다.

## 2단계 — 사실을 확인한다

**쓸 사실은 전부 근거가 있어야 한다.** 근거는 둘 중 하나다.

1. **아카이브 항목의 `title` 과 `summary` 에 실제로 적혀 있는 내용.**
   그 항목의 `source_name` 을 문장 안에 밝힌다 — "Hawaii News Now 는 9월 7일
   보도에서 …" 처럼. 이 요약은 우리가 그 매체 원문에서 받아 적어둔 것이라
   그 자체가 출처다.
2. `WebFetch` 로 원문을 열어 확인한 내용.

**외부 접속이 막혀 있으면 1번만으로 쓴다.** 클라우드 실행 환경은 웹 접속이
프록시에서 차단돼 있을 수 있다(2026-09-09 실측: 뉴스 사이트도 구글도 환율
API도 전부 403). 그때는 WebFetch 를 포기하고 아카이브만으로 쓴다.
**접속이 막혔다는 이유로 0편을 내지 마라** — 아카이브에 근거가 있으면 충분하다.

다만 이 둘은 지킨다.

- **아카이브에 없는 숫자는 쓰지 않는다.** `summary` 에 "카테고리 4" 가 있으면
  쓰고, 풍속이 적혀 있지 않으면 풍속을 쓰지 않는다. 기억으로 채우지 마라.
- **제목만 보고 쓰지 않는다.** `summary` 까지 읽는다. 제목은 매체가 붙인
  것이라 본문과 어긋날 때가 있다.

WebFetch 를 못 썼으면 보고에 "외부 접속 차단으로 아카이브만으로 썼다"고 적는다.

**지어내지 않는다.** 확인 못 한 것은 쓰지 않는다. 네가 갖고 있지 않은 현장
감각을 지어내지 마라. 너는 자료를 이어 붙여 맥락을 만드는 일을 한다.

## 3단계 — 쓴다

`content/review/YYYYMMDD_영문슬러그.md` 를 만든다. 앞머리는 정확히 이 형식이다.

```
---
id: art-<region>-<슬러그>-<YYYYMMDD>
region: <guam|saipan|hawaii|vietnam|kota|laos|jeju|japan|thailand|taiwan>
section: <news|flight|data>
title: 제목
source_name: ''
source_url: ''
summary: 두세 문장 요약
status: approved
---

본문
```

`source_name` 과 `source_url` 은 **빈 값**이다. 우리가 쓴 글이라 원문이 없다.

### 문체

**`content/review/20260908_kal_jal.md` 와 `20260908_chuseok_search.md` 를 먼저
읽고 같은 결로 써라.** 요약하면 이렇다.

- 첫 문단에 결론을 놓는다. 뜸 들이지 않는다
- 소제목은 `##` 로 나눈다
- 핵심 숫자는 **굵게**
- 비교·목록은 표로
- 인용은 매체명과 날짜를 문장 안에 밝힌다 — "뉴데일리는 9월 4일 보도에서"
- 마지막에 `## 알아둘 점` 을 불릿으로. 독자가 실제로 해야 할 일
- 맨 끝에 `**출처** ·` 줄
- 지역면 링크는 내부 경로로 — `[일본 지역면](/japan/)`
- 과장하지 않는다. 담담하게. 제목은 명사나 평서형으로 끝낸다

## 4단계 — 발행

```bash
python -m pytest -q          # 통과해야 한다
git add content/review/
git commit -m "해설 기사를 싣는다: <제목>"
git push
```

푸시하면 `content/review/**` 감시 트리거가 워크플로를 돌려 **몇 분 안에**
사이트에 실린다. 따로 배포할 필요 없다.

## 5단계 — 영문 제목을 우리말로

현지 영문 매체에서 온 기사는 제목이 영문이다. 한국 독자에게 벽이다. 해설을 다
쓴 뒤(못 쓴 날도) 그날 영문 제목을 우리말로 옮긴다.

```bash
python -m src.title_ko todo --limit 40     # 번역 안 된 영문 제목 목록(JSON, 최신순)
```

목록의 id 마다 한국어 제목을 붙여 JSON 파일로 저장한다. id 는 앞 8자만 써도 된다.

```json
{"cdbbca51": "코나공항 활주로 균열로 또 폐쇄, 항공편 3편 회항",
 "8c30d3bd": "~"}
```

```bash
python -m src.title_ko merge /tmp/ko.json   # data/title_ko.json 에 합친다(검사 포함)
git add data/title_ko.json
git commit -m "영문 제목 N건을 우리말로"
git push
```

푸시하면 `data/title_ko.json` 감시 트리거가 사이트를 다시 만든다. 주소는
원제목으로 유지되고, 기사 페이지에 원제가 병기된다.

제목 규칙:

- **신문 제목이다.** 명사로 끝내고 60자 안에. 원문에 없는 사실을 넣지 않는다
- 지명은 우리 표기로 — 오아후·카우아이·마우이·와이키키·코타키나발루·사바·
  하노이·호치민·다낭·나트랑·푸꾸옥·비엔티안·사이판. 매체 브랜드("First Alert
  Forecast:")는 뗀다. "Hurricane Lowell Update 3" 은 "허리케인 로웰 3보: …"
- 원문이 '우리(We)' 시점의 블로그 글이면 3인칭 사실로 바꾼다
- **지역과 무관한 기사**(다른 나라 소식, 지역 사건·사고, 외신 잡보)는 번역하지
  말고 값을 `"~"` 로 적는다. 다시 목록에 안 뜬다. 보고에 건수와 이유를 적는다
- 40건이 넘으면 최신 40건만. 나머지는 다음 날

## 하지 말아야 할 것

- **`data/published_index.json` 을 건드리지 마라.** 재발행을 막는 유일한
  장치다. 망가지면 같은 기사가 다시 나가거나 새 기사가 영영 안 나간다
- `data/items/*.jsonl` 을 손으로 고치지 마라
- 로컬에서 `python -m src.build` 나 `src.publish_drafts` 를 돌려 커밋하지 마라.
  발행은 CI 가 한다
- 사진을 올리지 마라 (얼굴 검사를 건너뛴다)
- 가격·연락처·개인정보를 본문에 넣지 마라. 발행 경로에서 차단된다

## 몇 편을 쓰나

**하루 1~3편. 0편도 괜찮다.**

쓸 만한 소재가 없는 날은 **아무것도 쓰지 않는다.** 빈 글을 채우는 것이 안 쓰는
것보다 나쁘다. 그런 날은 "오늘은 쓸 소재가 없었다"고 이유와 함께 보고하면 된다.

## 마치며 보고할 것

- 무엇을 몇 편 썼는지, 각 편의 제목과 근거
- 확인하려다 못 한 사실이 있으면 그것
- 테스트·푸시 결과
- 우리말로 옮긴 제목 수, `"~"` 로 건너뛴 수와 이유
- 소재가 없어 안 썼으면 그 이유

## 푸시가 안 되면

`git push` 가 거부되면 **에러 메시지를 그대로 보고에 붙여라.** 클라우드에서
저장소에 밀 권한이 있는지는 아직 실물로 확인되지 않았다(2026-09-08 기준).
안 되면 원인을 알아야 고친다.

밀지 못했더라도 쓴 초안은 그대로 두고 보고만 하면 된다. 다음 실행에서
`status: approved` 인 초안을 발견하면 그때 밀린다.

## 이미 오늘치가 있으면

`content/review/` 에 오늘 날짜(YYYYMMDD)로 시작하는 파일이 이미 세 편 있으면
더 쓰지 않는다. 하루 상한은 세 편이다.

두 편 이하라면 남은 자리만큼만 쓴다. 억지로 채우지 않는다.
