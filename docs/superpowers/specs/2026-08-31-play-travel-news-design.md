# 플레이 여행신문 — 설계 문서

작성일: 2026-08-31
상태: 승인됨 (사용자 승인 2026-08-31)

---

## 1. 목적

플레이 계열 7개 여행지의 여행 정보를 매일 자동으로 수집·발행하는 자사 미디어 허브를
구축한다. 검색으로 유입된 여행객이 실용 정보를 확인하고 같은 사이트 안에서 플레이
상품 예약으로 넘어가는 두 번째 관문을 만드는 것이 사업적 목적이다.

**언론사 등록은 하지 않는다.** 인터넷신문 등록은 상시고용 취재·편집 인력 요건과
자체기사 비율 규정을 실제로 충족해야 하므로 현 단계에서 부담이 크다. 자사 미디어로
운영하다가 트래픽이 쌓이면 등록으로 승격하는 경로를 열어둔다.

### 대상 지역 (7개)

`brands.json` 레지스트리와 동일하게 유지한다.

| key | 지역 | 브랜드 |
|---|---|---|
| guam | 괌 | 괌플레이 |
| saipan | 사이판 | 사이판플레이 |
| hawaii | 하와이 | 하와이플레이 |
| vietnam | 베트남(다낭) | 베트남플레이 |
| kota | 코타키나발루 | 코타플레이 |
| laos | 라오스 | 라오스플레이 |
| jeju | 제주도 | 제주도플레이 |

> 과미(@guami_travel)는 플레이 계열이 아니다. 이 사이트에 과미 콘텐츠는 넣지 않는다.

## 2. 성공 기준

1. 사람이 하루 손을 놓아도 사이트가 매일 갱신된다. (A·B등급 무인 발행)
2. 타 매체 기사 전문을 복제하지 않는다. 위반 시 빌드가 실패한다. (코드로 강제)
3. 같은 기사를 두 번 발행하지 않는다. (중복 가드 fail-closed)
4. 운영 비용이 도메인비를 제외하면 0원이다.
5. 각 기사 페이지에서 해당 지역 플레이 상품으로 가는 경로가 존재한다.

## 3. 아키텍처

```
매일 05:00 KST — GitHub Actions (맥 전원과 무관하게 동작)
        │
   ① 수집기 collect.py
        │  sources.yaml 을 읽어 7지역 × 6소스군 병렬 수집
        │  출력: data/raw/YYYY-MM-DD/<source_id>.json
        │
   ② 편집기 edit.py
        │  중복 제거 → 등급 분류 → 저작권 가드 → 지역 태깅
        │  출력: data/items/YYYY-MM-DD.jsonl, content/review/*.md (C등급 초안)
        │
   ③ 빌더 build.py
        │  Jinja2 템플릿으로 정적 HTML + RSS + sitemap 생성
        │  출력: public/
        │
   ④ 배포 GitHub Pages (커스텀 도메인)
        │
   ⑤ 확산 OSMU — 네이버 블로그·인스타·뉴스레터 (기존 자동화 재사용)
```

### 기술 스택

- Python 3 + Jinja2 + feedparser + httpx (기존 자산과 동일 계열, 의존성 최소)
- 정적 사이트. 데이터베이스 없음. 상태는 전부 저장소 안의 파일.
- GitHub Actions (스케줄 + 빌드) / GitHub Pages (호스팅)

**정적으로 가는 이유:** 뉴스 사이트는 본질적으로 읽기 전용이다. 워드프레스는 월
호스팅비·보안 업데이트·속도 저하를 떠안는데 그 대가로 얻는 동적 기능이 이 사이트에는
없다. Pages는 이미 `guamplay-media`로 운용 중이라 인프라가 검증돼 있다.

## 4. 콘텐츠 3등급 분류 — 이 설계의 핵심

수집한 모든 항목은 셋 중 하나로 분류된다. 등급이 저작권 처리와 발행 경로를 동시에
결정한다.

| 등급 | 내용 | 출처 성격 | 저작권 | 발행 |
|---|---|---|---|---|
| **A. 사실 데이터** | 환율·날씨·수온·여행경보·항공 스케줄·입국규정 | 공공API·공식 발표 | 사실은 저작물이 아님 | **무검수 자동** |
| **B. 큐레이션** | 원문 제목 + 출처 링크 + 짧은 요약 | 타 매체 | 인용 범위 내 | **무검수 자동** |
| **C. 해설 기사** | 우리가 직접 쓴 분석·정리·가이드 | 자체 생산 | 우리 저작물 | **검수 후 발행** |

**왜 나누는가:** 항공 스케줄 오보 하나가 실제 예약 사고로 이어진다. 동시에 모든
콘텐츠에 사람 검수를 걸면 자동화가 성립하지 않는다. A·B는 원문을 판단 없이 옮기므로
오보 위험이 원출처 수준이고, C만 우리가 해석을 얹으므로 여기에만 게이트를 건다.

**중요한 성질:** 사용자가 며칠 검수를 안 해도 A·B만으로 사이트는 매일 갱신된다.
검수는 품질을 올리는 장치이지 발행의 필요조건이 아니다.

## 5. 저작권 가드 (copyright_guard.py)

빌드 파이프라인에 강제 삽입한다. 위반 항목이 하나라도 있으면 **해당 항목을 버리고
경고를 남긴다.** 반복 위반 시 빌드를 실패시킨다.

### 규칙

1. **B등급 인용 상한** — 원문에서 가져오는 텍스트는 최대 2문장 또는 200자. 초과 시 절단이
   아니라 폐기(요약을 우리가 못 썼다는 뜻이므로).
2. **출처 필수** — 모든 B등급 항목은 `source_name`과 `source_url`이 있어야 한다. 없으면 폐기.
3. **원문 이미지 임베드 금지** — 타 매체 이미지 핫링크·복제 금지. 사용 가능한 이미지는
   ① 자체 보유 실사(NAS DSLR 라이브러리) ② 공식 배포 이미지(관광청·항공사 프레스킷,
   출처 표기) ③ 자체 생성 그래픽뿐이다.
4. **robots.txt 준수** — 수집 대상 사이트의 robots.txt를 확인하고 금지된 경로는 수집하지
   않는다. User-Agent를 명시하고 요청 간 지연을 둔다.
5. **전문 저장 금지** — 원문 본문 전체를 저장소에 커밋하지 않는다. 수집 단계에서
   제목·요약·링크·메타데이터만 남긴다.

## 6. 중복·재발행 방지 (dup_guard)

기존 발행 자동화의 원칙을 그대로 가져온다. 한 번 낸 것을 또 내는 것은 금지다.

- `data/published_index.json` — 발행된 모든 항목의 `id`와 제목 해시를 누적 보관한다.
- `id` = 정규화된 원문 URL의 SHA1. URL이 없으면 `제목+발행일` 해시.
- 제목 유사도 중복 — 같은 사건을 여러 매체가 보도한 경우, 정규화 제목의 토큰 자카드
  유사도가 0.7 이상이면 같은 사건으로 묶고 대표 1건 + 나머지는 "관련 보도" 링크로 처리한다.
- **fail-closed** — 인덱스 파일을 읽지 못하면 발행을 중단한다. 읽기 실패를 "중복 없음"으로
  해석하지 않는다.

## 7. 데이터 모델

### 7.1 소스 정의 `sources.yaml`

```yaml
- id: guam_pdn
  region: guam
  section: news
  name: Pacific Daily News
  type: rss              # rss | api | html | naver
  url: https://.../rss
  lang: en
  enabled: true
```

### 7.2 항목 스키마 (수집·편집 공통)

```json
{
  "id": "sha1...",
  "grade": "A|B|C",
  "region": "guam",
  "section": "flight|news|data|promo",
  "title": "...",
  "summary": "...",
  "body_md": "...",
  "source_name": "Pacific Daily News",
  "source_url": "https://...",
  "published_at": "2026-08-31T05:00:00+09:00",
  "collected_at": "2026-08-31T05:00:12+09:00",
  "status": "draft|approved|published",
  "title_hash": "...",
  "related": ["id1", "id2"]
}
```

`body_md`는 C등급에만 존재한다. A·B는 `summary`까지만 가진다.

## 8. 수집 소스 (후보 — 구현 1단계에서 실측 검증 필요)

**미검증 항목:** 아래 소스들의 RSS/API가 현재 살아있는지는 아직 확인하지 않았다. 구현
1단계는 이 목록을 전수 조사해 실제 응답하는 것만 `sources.yaml`에 남기는 작업이다.
죽은 소스는 조용히 빼지 말고 조사 결과에 기록한다.

## 9. 사이트 구조

```
/                        오늘의 여행신문 — 전 지역 헤드라인
/guam/                   지역 홈 — 오늘의 데이터 패널 + 최신 기사
/guam/<slug>/            개별 기사
/saipan/ /hawaii/ /vietnam/ /kota/ /laos/ /jeju/
/flight/                 항공 소식 전체 (지역 교차)
/data/                   실용 데이터 대시보드 (환율·날씨·경보 한눈에)
/archive/2026/08/31/     날짜별 아카이브
/about/                  매체 소개·저작권 정책·연락처
/rss.xml  /sitemap.xml  /robots.txt
```

### 지역 홈 상단 데이터 패널

각 지역 페이지 최상단에 A등급 데이터를 고정 배치한다. 매일 값이 바뀌므로 재방문
동기가 되고, 검색엔진에도 매일 갱신되는 페이지로 인식된다.

```
괌  |  환율 1,3xx원  |  오늘 31°C 흐림  |  수온 29°C  |  여행경보 1단계
```

### 상품 연결

모든 지역 페이지와 기사 하단에 해당 지역 플레이 상품 링크 블록을 넣는다. 이것이
이 사이트를 만드는 사업적 이유다.

## 10. 검수 워크플로 (C등급)

### C등급 후보 선정 규칙

무엇을 해설 기사로 쓸지는 자동으로 정해진다. 아래 셋 중 하나에 해당하면 후보가 된다.

1. **같은 사건을 3개 이상 매체가 보도** — 중요한 사건이라는 신호. 묶어서 정리 기사로 쓴다.
2. **네이버 데이터랩 급상승 여행 키워드와 겹치는 항목** — 검색 수요가 실재한다는 신호.
3. **항공 신규취항·증편·감편** — 예약 의사결정에 직접 영향을 주므로 항상 해설을 붙인다.

하루 후보 상한은 5건이다. 초과 시 위 순서로 우선한다. 상한을 두는 이유는 검수 부담이
하루 감당 가능한 양을 넘으면 검수 자체가 중단되기 때문이다.

### 절차

1. 새벽 수집 후 C등급 후보가 `content/review/`에 `status: draft`로 쌓인다.
2. 매일 아침 클로드 예약작업이 초안을 작성하고 목록을 사용자에게 제시한다.
3. 사용자가 승인한 항목만 `status: approved`로 바뀌어 다음 빌드에 포함된다.
4. **48시간 내 승인되지 않은 초안은 자동 폐기한다.** 뉴스의 신선도가 지났고, 오래된
   초안이 쌓이면 검수 자체를 안 하게 된다.

**AI 기사 작성 비용:** Actions에 API 키를 넣으면 완전 무인이지만 월 과금이 붙는다.
대신 클로드 예약작업(현재 틱톡 발행에 쓰는 방식)이 정액 구독 안에서 처리한다.
추가 비용 0원.

## 11. 오류 처리

- **개별 소스 실패는 전체를 막지 않는다.** 소스 하나가 타임아웃/404여도 나머지로 빌드한다.
  실패는 `data/raw/YYYY-MM-DD/_errors.json`에 기록한다.
- **연속 실패 감시** — 한 소스가 3일 연속 실패하면 리포트에 경고를 올린다. 조용히 죽은
  소스를 방치하지 않기 위함이다.
- **가드는 fail-closed** — 중복 인덱스나 저작권 가드가 동작 불능이면 발행을 중단한다.
  안전 장치의 침묵을 통과로 해석하지 않는다.
- **빈 결과 방어** — 수집 결과가 0건이면 이전 빌드를 유지하고 경고한다. 빈 사이트를
  배포해 기존 페이지를 지우지 않는다.

---

## 12. 테스트 전략

- `collect.py` — 저장된 RSS/JSON 픽스처로 파싱 검증. 네트워크 없이 돈다.
- `copyright_guard.py` — 인용 200자 초과, 출처 누락, 이미지 핫링크 각각에 대한 폐기 테스트.
- `dup_guard` — 동일 URL, 유사 제목, 인덱스 읽기 실패(fail-closed) 3케이스.
- `build.py` — 항목 0건·1건·다수 케이스에서 유효한 HTML/RSS/sitemap이 나오는지.
- 통합 — 픽스처 입력으로 전체 파이프라인을 돌려 `public/`이 생성되는지 확인.

| 기사 작성 | 0원 (클로드 정액 구독 내) |

## 14. 구현 순서

각 단계는 독립적으로 검증 가능하다.

1. **소스 실측 조사** — 8절 후보를 전수 확인해 `sources.yaml` 확정. 산출물: 조사 보고서 + yaml.
2. **수집기** — `sources.yaml` → `data/raw/`. 픽스처 테스트 포함.
3. **편집기** — 중복 제거·등급 분류·저작권 가드.
4. **빌더** — 정적 HTML/RSS/sitemap. 이 시점에 로컬에서 사이트를 눈으로 볼 수 있다.
5. **자동화** — Actions 워크플로 + Pages 배포.
6. **도메인 연결** — 도메인 구매·DNS(사용자 작업) + Pages 커스텀 도메인 설정.
7. **검수 워크플로** — 클로드 예약작업 연동.
8. **OSMU 확산** — 블로그·SNS·뉴스레터.

1~4단계까지가 "매일 갱신되는 신문 사이트"의 최소 완성이다. 5단계에서 무인화되고,
6단계부터는 성장 작업이다.

**이 스펙에 딸린 구현 계획은 1~5단계까지만 다룬다.** 6~8단계(도메인·검수 연동·OSMU)는
각각 선행 단계의 결과에 의존하므로, 5단계가 끝난 뒤 별도 사이클로 다시 설계한다.
한 계획에 8단계를 전부 넣으면 뒤쪽이 추측으로 채워진다.
